# P07 — Declared tuning objectives and winner evidence

Native hyperparameter tuning could silently replace the accepted objective, ignore unsupported features, discard failed configurations and report completion after a failed winner refit. Curves could display invented zero spread for unavailable points, and the interface could advance failed/stopped results as completed work.

The current tuning API and search driver resolve the accepted classification/regression objective and direction once. Binary classification supports ROC-AUC, PR-AUC, log loss, Brier score, expected cost, accuracy, F1, precision, recall and KS; regression supports R², RMSE, MAE and MSE. Metric aliases resolve consistently. Contradictory metrics/directions, task-incompatible metrics, invalid feature lists and nonfinite thresholds/bounds fail explicitly. Accepted threshold metrics use 0.5; expected cost uses declared false-positive/false-negative costs per observation. Historical inputs can retain F2/MCC and an explicit alternate threshold, with their upstream provenance unverified. Multiclass tuning remains blocked.

Every successful configuration retains complete metric coverage, individual fold metrics, fold-local transformation provenance and native fit receipts. Only complete finite primary CV metrics can select a winner. Undefined R² stays null, and no unavailable objective can silently select a fixed/default configuration. Classification's fixed native AUC early-stopping criterion requires both classes in each governed training/validation partition, including when the selection objective itself is a loss. Automatic train-label-ratio weights are recomputed from each training fold; fixed weight policies remain fixed. Candidate publication's separate development CV freezes the selected fitter parameters and remains explicitly post-selection evidence.

The search basis binds the selected execution, ordered prepared/raw development inputs and labels, objective/costs, validation/transformation policy, parameter space and fixed values, sampling seed, method resolution, folds, worker/curve budgets, native fitter budget, runtime versions and runner source digests. Protected final-outcome rows do not enter these hashes. Grid/random ties preserve configuration order rather than worker completion order. Optuna executes sequential seeded trials; unavailable objectives are pruned, failed attempts remain recorded and an unavailable Optuna backend has an explicit random fallback reflected in the basis. Native fitter seeds/criteria remain separately visible in fit receipts.

Attempt receipts preserve each configuration, index, objective coverage, failure/cancellation status and available error. Failed curve points retain an error and null mean/spread, and cannot generate a false optimum or range suggestion. Successful curve points retain their exact parameters, fold scores and fit receipts. Optional curve failures can coexist with a valid selected winner; failure counts remain visible. Surrogate importance and range suggestions are descriptive ranking heuristics, not causal effects. Fold means are unweighted, and fold spread is not a confidence interval.

Only a completed search with an exact selected configuration enters winner refit/publication. Search errors, cooperative stops and refit/publication failures cannot report completed tuning. Terminal status is published after persistence/publication finishes; preparation errors also replace the stale per-file result with error evidence. Governed winner publication stores `tuning_selection.json` inside the immutable candidate manifest, validates its execution/configuration/basis digest and preserves the parent. Candidate manifest checks detect subsequent evidence corruption. Historical model refits use new candidate paths instead of overwriting an earlier model file.

The existing tuning request remains an instruction to adopt the resulting **development** candidate if the parent is still current. A changed parent produces a detached candidate without replacing the current execution; the interface blocks its promotion. This is technical development adoption, not independent review, production approval or acceptance in use. Cancellation is cooperative at search/curve boundaries; an active native fit/publication is not forcibly interrupted.

Browser starts bind the displayed execution. Completed, failed and stopped results remain distinct in checkpoints, roadmap progress and promotion controls. Failed evidence is inspectable, development validation is labeled correctly, undefined chart values stay gaps, and technical objective/coverage/fit information remains inside native expandable Details. Historical results without completion status cannot silently enable promotion.

These results reuse development data for search, early stopping, curves and post-selection assessment. They are **exploratory evidence**, not nested validation, independent reproduction, paired effects/uncertainty or proof of customer value. Native training/early stopping still uses fixed AUC/RMSE; complete fitter alignment remains open. Per-file result projections and in-process progress remain mutable; failed searches can be superseded by later searches. This packet does not deliver immutable durable search jobs, concurrent per-file jobs, authenticated signatures, storage/controller tamper resistance, expert Python isolation, full project roles/egress, production recovery or independent review/reproduction. Security, accessibility milestone and partner/value gates remain open.
