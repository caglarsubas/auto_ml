# Private broker CA-only TLS trust (P46)

The private broker previously used Redis/Kombu's standard SSL connection with a CA filename, which could add system roots to declared trust. Private execution now selects `execution_jobs.broker_transport:Transport` per Celery application. The sealed transport derives synchronous producers and asynchronous consumers from a built-in connection that creates `SSLContext(PROTOCOL_TLS_CLIENT)`, loads only captured declared CA bytes, requires certificate and hostname verification, and enforces TLS 1.2 minimum. It does not register or monkeypatch a shared external transport.

`load_job_config` captures a bounded, regular, single-link, non-symlink CA file, rejects group/other writable files and malformed/changed input, and validates certificate data locally. Captured bytes travel in broker SSL options, so reconnection cannot silently adopt a replaced CA path. CA certificates are public: existing read-only public certificate deliveries remain supported; fresh installation files still use the protected ownership/modes of the installation contract. TLS option downgrade, implicit CA path replacement and plaintext/failover URL lists are blocked. Historical development Redis/rediss retains its existing transport explicitly.

Dependency readiness uses the same private configuration and connection class. API preflight, dispatcher publishing and worker consumption use the private Celery application. Runtime source manifests bind the transport implementation; the plan's URL/CA file interface remains unchanged, and saved plans/roots/credentials are never implicitly rotated or rewritten. Existing runtime images are not retrospectively qualified by this change.

Kombu's [connection interface](https://docs.celeryq.dev/projects/kombu/en/stable/reference/kombu.connection.html) accepts a transport implementation. Compatibility is checked against the pinned Redis/Celery/Kombu dependencies in sealed images. Internal channel extension points remain dependency-version sensitive; future dependency upgrades must rerun native transport and queue qualification.

## Acceptance

New cases cover CA snapshot semantics, unsafe delivery, trust downgrade refusal, no system-root loading, producer/asynchronous-consumer classes and independent development behavior. The owned fresh Linux fixture performs actual API publish, worker consume, dispatcher publish and API acknowledgement on a unique synthetic queue, checks AOF remains enabled, and rejects unauthenticated, wrong-password, cache-credential, plaintext, wrong-CA, wrong-hostname and ambient-root bypass attempts. All existing startup, schema/accounts/adoption/HTTPS, cache TLS/recovery, broker loss/outbox recovery, duplicate delivery, scoring replay, scientific, metadata and browser checks remain required under their original budgets.

Local ARM component results do not qualify Linux-root installation or customer deployment. Hosted exact-head receipts must verify actual adopted roles, exact exported image identities and exclusively owned cleanup before merge. PR and separate main CI results are recorded independently. D07, complete production recovery, upgrades/rollback, expert isolation, release and customer acceptance remain open.
