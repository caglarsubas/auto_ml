# Fresh private schema initialization (P42 / D07)

The Linux installation operator runs `scripts/private_schema_init.py` after exact dependency startup and before application adoption. With `--plan` and `--expected-manifest-sha256` it describes the sealed image's migration graph and database state without publishing intent or changing schema. Review that description, then pass its exact `--schema-sha256` to initialize a fresh database. An existing or partial schema without this initializer's exact intent requires a separately reviewed migration workflow.

The graph digest binds the immutable runtime inventory, migration vertices, dependencies and targets. Execution uses the exact pinned API image as UID/GID 10001, with a read-only root, bounded CPU/memory/PIDs, no capabilities, fixed private networking and one read-only application-secret mount and an ephemeral media directory. It receives neither customer artifacts, the PostgreSQL owner credential nor the Docker socket. The helper verifies the runtime inventory before importing Django and connects using the ordinary non-elevated application role over hostname-verified PostgreSQL TLS. It checks actual role flags/memberships, acquires a bounded nonblocking database advisory lock, and refuses unexpected namespaces, extensions, functions/event triggers, relation owners, tables, sequences or migration history. Current-state verification checks history and table coverage; it does not claim complete column/index/constraint drift detection.

Before DDL the controller publishes a root-only, immutable intent binding the plan, dependency preparation/profile, three exact dependency identities, image, graph and trusted helper code. A shared installation lock serializes dependency/schema operations. PostgreSQL applies migration DDL, migration records and `post_migrate` seeds in one transaction; failure rolls them back together. No fake, reverse, skip or automatic repair operation is available. Final publication rechecks the same active exact dependency profiles and identities.

A successful retry verifies current state and preserves the original receipt bytes. If a committed result was not published but exact intent remains, recovery verifies the current schema and explicitly records `recovered_current_from_exact_intent`, without claiming to have observed the original execution. Changed intent, recorded state, runtime or dependency identities block. New receipts use fsync and Linux atomic no-replace publication. An interrupted staging write or malformed historical file blocks for operator inspection; the controller does not overwrite or delete it. Host root and independently trusted graph/image inputs remain the installation trust boundary.

Acceptance extends the existing fresh owned Linux-root dependency fixture: read-only description, wrong digest before intent, actual DDL and post-migration seeds, repeat without reexecution/republication, lost-result recovery, foreign-table rejection and preserved history. A qualification-only helper injects an exception *after actual migration DDL inside the transaction*, then verifies an empty schema; the production helper and approved intent are unchanged. Unit checks cover altered bindings/approvals, concurrent operations, forbidden early services, late dependency changes, static failure output and failed/no-replace publication. All earlier scientific, metadata, native/private recovery and browser gates retain their original assertions and budgets. Final exact-head Linux acceptance is required before merge.

This initializes schema only. It does not enroll accounts, start application services, authorize models or qualify customer installation. Account enrollment, authenticated cache/TLS, complete storage/policy/supply/upgrade/recovery and expert isolation qualification, independent reproduction, accessibility and release/value/customer gates remain open. Existing migrations and legacy data remain inspectable; upgrades require separate reviewed scope.
