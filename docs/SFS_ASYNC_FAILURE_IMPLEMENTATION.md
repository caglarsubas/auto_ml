# SFS publication and async failure diagnostics (P54)

SFS candidate publication can fail with `OperationalError: database is locked` when its SQLite metadata transaction reads before a competing writer acquires the write reservation. The UI then sees only `status: error`; the previous browser poll discarded the accompanying error payload, so a retry obscured the underlying cause.

The development/CI SQLite profile now starts atomic transactions in `IMMEDIATE` mode, reserving the writer before reads. The existing SQLite timeout remains unchanged, and request-wide atomic transactions are not enabled. Private PostgreSQL configuration and TLS policy are unchanged. Long-running fitting, evaluation and CV remain outside artifact-registration transactions. This does not turn SQLite into the supported private-deployment database or promise unlimited concurrency. [Django transaction behavior](https://docs.djangoproject.com/en/5.2/ref/databases/#transactions-behavior), [SQLite transactions](https://sqlite.org/lang_transaction.html).

An accepted SFS request receives an operation ID. Search, candidate-refit, candidate-publication and final-evidence-write failures retain that ID, dataset/execution references, exception type, stage and bounded stack-frame locations in status and saved evidence where writing succeeds. Structured service diagnostics exclude exception values, source text, locals, rows and parameters. Existing authorized error detail remains available to the dataset owner. Terminal success still follows candidate publication and evidence writing; failed searches cannot publish successful candidate evidence.

The browser's existing 30-second status assertion now retains the selected error/status fields in an attachment and the failure message before cleanup or retry. It does not retain headers, cookies, credentials or data frames. Reporter failures cannot replace the original assertion. No scientific fixture, assertion, timeout, skip, coverage or retry budget is relaxed.

Qualification reproduced the publication failure in an owned synthetic installation with a second metadata writer active during SFS. The correlated failure stack traversed `publish_candidate`, `publish_execution` and `register_artifact`; the same fixture passed on the first attempt after the transaction change. Twelve ordinary repeated workflow cases also passed before the transaction change. A native two-connection regression fails against the preceding configuration and verifies both writers commit with the reservation policy. Injected search/refit/publication/final-write faults verify failure correlation and prevent false completion. The local fixture's startup/absent-worker/Redis-identity issues and an initial fault-fixture mismatch are retained separately from product failures.

The original historical CI retry did not record its exception payload, so its exact cause cannot be reconstructed as certainty. The reproduced matching SFS publication race is fixed, and future failed polls retain actionable evidence. Disk-only status handling after interrupted processes remains a successor task; thread-based SFS is not a qualified distributed job service. Full D07 lifecycle, recovery, expert-isolation and release/customer gates remain open.
