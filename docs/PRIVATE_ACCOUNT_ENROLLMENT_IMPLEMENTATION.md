# Ordinary private account enrollment and fresh adoption (P43 / D06, D07)

The installed `enroll_account` Django management command creates an ordinary active account with one explicitly requested project role. It requires actual private PostgreSQL TLS/current-schema/non-elevated-role and authenticated broker preflight. The first project uses `--new-project` with `--role admin`; later accounts use `--project-id` and developer, reviewer or admin. Staff/superuser flags, global groups/permissions, credential reset, legacy data adoption and model-use approvals are outside this command.

Supply an exact username, request UUID, asserted `--operator-label`, role and project scope. `--password-file` must be a private regular file owned by the calling runtime identity, with mode 0400 or 0600, one link, no final symlink and at most 4096 bytes. Read metadata/content are rechecked. Initial credentials require at least 16 characters/eight distinct characters and the configured Django validators. Do not put a password on the command line. Supported installation execution uses the sealed image as UID/GID 10001 with read-only application/credential inputs and ephemeral media; host operator access remains its trust boundary.

A single metadata transaction creates the user, session authority, project/membership, durable project-isolation policy and attributable enrollment/project records. Project isolation activates durably and legacy resources require their existing explicit operator-adoption workflow. The label records an operator assertion, not authenticated human identity. The UUID binds exact nonsecret scope and label; passwords and independent password digests never enter request/evidence hashes, stdout or audit details. Django stores its normal credential hash. Failed requests leave no account/authority/project audit publication; database sequence gaps may remain.

An exact retry checks the same active ordinary account, delivered credential, session revision and project-membership revision/role, then returns the original receipt without credential/hash upgrade or authority/history rewriting. Changed scope, labels, password, account/global privilege, authority, deleted policy or colliding derived project-operation receipts block. An existing username is never silently adopted or reset. These application checks do not certify resistance to privileged database/audit tampering.

Adoption preflight now runs the unchanged sealed launcher through a fixed isolated wrapper with its own ephemeral media directory and no customer artifact mount. This lets preflight complete while the fresh artifact root is empty. Actual API/worker/dispatcher startup remains responsible for its normal writable media initialization. Exact image/profile/UID/network/resource and actual TLS/schema/broker/role checks still apply before application launch.

Qualification extends the exclusively owned Linux-root dependency fixture through fresh schema, three real management-command enrollments, exact retries and password/project failure rollback, altered assertion/privilege rejection, four-service adoption from empty artifact storage, repeated service identities, real CA/hostname-verified HTTPS/CSRF login/project roles/logout and developer/reviewer administrator-escalation rejection. Fixtures remove only their owned resources and retain all earlier startup/restart/fault/recovery checks. The original host, full-test, skip, coverage and browser retry budgets remain unchanged. Final exact-head acceptance is required before merge.
