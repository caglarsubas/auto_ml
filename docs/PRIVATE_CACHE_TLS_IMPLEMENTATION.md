# Private cache authentication and TLS

P44 upgrades newly rendered plans to `private_installation_plan_v3`, prerequisites to v3, dependency profiles to v3 and configuration recipes to v2. Cache and durable job broker remain separate Redis instances with distinct decoded passwords. The cache still uses no disk persistence, a 96 MiB LRU data limit, a 128 MiB container limit, a private network and no published ports. This is a technical installation step; D07 and the release/customer gates remain open.

New app delivery contains nine protected files. Add `app/cache-url` with a percent-encoded strong password in `rediss://:PASSWORD@cache:6379/0` and `app/cache-ca.crt` with the selected trust anchor. Deliver a separate `cache/server.crt` and `cache/server.key` alongside the previous five dependency files. The existing root/UID/GID/mode/single-link/ACL/budget guards and current OpenSSL chain, server-name and key-pair verification apply to the cache too. Dependency preparation is fresh-only and publishes the same bound nonsecret immutable receipts, with the new exact profile digest and seven-file delivery count.

The fixed cache recipe disables plaintext (`port 0`), requires password authentication and protected mode, enables only TLS 1.2/1.3 on port 6379, and disables CONFIG/DEBUG/MODULE. Client certificates are not required; password authentication remains required over verified server TLS. The application reads bounded owner-only regular single-link URL and CA files, captures their contents before use, requires certificate and hostname verification and TLS 1.2 or newer, and rejects URL queries, alternate endpoints/databases, weak/control/malformed credentials, direct values and contradictory REDIS_URL settings. The cache and embedding clients use the same factory. A failed cache operation remains a cache miss/failure rather than authoritative modeling evidence; no fallback endpoint is selected.

API, worker and dispatcher startup preflight make a real authenticated cache TLS connection when the versioned file contract is selected. The dependency controller's bounded sealed-image probe checks actual cache TLS/authentication and disabled AOF using six read-only application credential/CA files. No owner credential, artifact or Docker-socket authority is added. Current captured files/configuration/certificates are rechecked before adopting or reusing services. Password/URL/payload/driver diagnostics are removed from cache and embedding logs and cache failure span attributes; failures carry static codes. The configuration still permits REDIS_URL for historical/development runtimes, which are not evidence for this hardened profile.

Saved v1/v2 plans remain verifiable against their original compositions and prerequisite definitions, without changing their bytes. Fresh dependency execution and application adoption require v3. Existing prepared roots/credentials/receipts are never rewritten or implicitly rotated. Prepare and review a fresh plan/root/image graph with the new delivery; migration of a customer installation requires a separately reviewed upgrade/recovery scope.

Qualification retains all preceding scientific, schema, enrollment, native packaging, metadata, recovery, HTTPS/browser and concurrency checks and budgets. A fresh owned Linux installation exercises actual API/worker cache and embedding factories, matched cache writes/reads, rejected unauthenticated/wrong-password/broker-password/plaintext/wrong-CA/wrong-hostname connections, unchanged memory/persistence limits, and only owned cleanup. A separate native ARM sealed-image fixture exercises the same production Redis recipe and client checks; it does not establish Linux host-controller or customer qualification. Initial portable fixture permission/digest/mount-count failures and absent-Redis telemetry failures are retained, then corrected or rerun with a real owned Redis service; no assertion, dataset, timeout, skip, coverage or browser-retry budget is weakened.

Storage encryption/capacity/retention, full egress and account lifecycle, supply authenticity, upgrades/rollback, production recovery, expert-code isolation and release/value/customer acceptance remain open. This packet neither changes a customer installation nor approves model use.
