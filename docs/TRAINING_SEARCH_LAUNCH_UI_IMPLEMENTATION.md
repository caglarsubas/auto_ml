# Reviewed development training launch — P119

The governed project workspace now exposes **Develop with queued training** for each dataset. This opens a separate, bounded development workflow using the P118 durable training/search API. It does not replace the legacy full modeling, SFS or broad hyperparameter-search controls.

A project developer declares binary classification or regression, the target and positive label, objective, development population, prediction horizon, outcome definition and label maturity. Numeric predictor names are entered one per line in explicit order. Random, group and ordered temporal validation require an explicit choice; group/time/outcome-window control fields follow the selected strategy. Built-in task metrics and nonnegative expected-cost parameters use the existing trusted backend semantics. Confirmations identify the development-only population and predictor availability; these statements do not independently establish data history.

**Prepare training preview** performs no queue submission. The server resolves the contract, exact input and plan digests, development-fold membership, runtime/source pins and complete budget. The panel shows their summaries and expandable exact declaration, folds and runtime. Editing any declaration or changing dataset, project or role invalidates the preview and its confirmation; stale responses are cancelled and ignored. Submission also compares the current options to the reviewed options. A separate confirmation and **Queue reviewed training search** submit the exact reviewed options and pins with a fresh request UUID. An unavailable service blocks admission. Server-side authority, CSRF, input/runtime/budget checks and partition restrictions remain authoritative.

An uncertain submission retains the exact body and UUID for **Retry exact training request**. It cannot start a replacement request while that outcome is unresolved. Leaving the panel discards this in-memory retry state; the UI tells the developer to inspect durable job history before starting replacement work. Rejected or stale requests require a new preview and review. Known assessment history has an explicit explanation: reuploading assessed rows does not establish fresh development provenance.

The existing job viewer supplies refresh, pagination, cancellation for eligible owners, attributable events, refreshed receipt downloads and completed native-model/fold evidence. It can reopen a job after leaving the panel. Training mode omits package-check/scoring launch controls. Read-only project members see job history without development controls. No result becomes a champion, package, review approval or production decision.

## Verification and limits

Additive frontend tests cover declaration semantics, group/time controls, low-cardinality regression, cost parameters, review invalidation, exact pins, service/role restrictions, stale previews, malformed receipts, context changes, and uncertain UUID-preserving retries. Three additive real browser scenarios use disposable session/CSRF accounts and actual durable workers: keyboard-driven binary preview/submit/evidence download/reopen; grouped regression with a real admitted request whose response is deliberately lost and then replayed with the same UUID; reviewer inspection with a forged preview denied and stale access cleared. Existing browser and unit cases remain unchanged. The disposable seeding helper adds isolated users/projects/data without modifying existing scientific fixtures.

The supported input remains a fresh headered UTF-8 numeric CSV up to 5 MiB, 30–1,000 rows, 40 columns and 1–32 predictors, with two or three explicit folds. Two fixed XGBoost depth candidates use 16 rounds and one thread. Backend budgets, lease fences, known assessment-history guards and full private TLS runtime qualification are unchanged. Predictor/target column names are explicit text; automatic column selection and data-history discovery are not provided. Unknown/external history and changed/reordered copies remain unverified. Expert code, broader algorithms and sizes, trial checkpoints, native model export/scoring, final assessment and reviewed model adoption remain open. Browser fixtures exercise the development transport; the existing private fixture separately qualifies the TLS PostgreSQL/broker/worker path. Neither is customer deployment, acceptance or recovery qualification. D07 and release gates remain open.
