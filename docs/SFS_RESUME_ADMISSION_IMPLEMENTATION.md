# Explicit SFS resume and search admission (P59)

SFS resume previously bypassed the strict recorded-state reader. A nested resume object could allow completed/failed records to start work, nested basis changes were checked only inside the worker, and malformed shapes could become HTTP 500. Step provenance and feature state were not validated before execution. A native stop during a later direction could omit the prior direction's current features, so subsequent resumption reported the wrong remaining pool.

Resume now reads strict saved evidence and admits only running, interrupted or stopped states whose outer and explicit nested bases match the accepted inputs, execution, objective, folds, runtime, implementation and budget. Steps must have contiguous integer indices, the declared direction and current basis digest, unique known features, and ordered single-feature additions/removals. Explicit feature and completed-step state must agree with those steps. Malformed baselines, unsupported prior metrics and ambiguous merged forward history block admission. Refusals return HTTP 409 with `resume_blocked` before registration or worker creation and leave evidence bytes unchanged.

New records name their active direction fields, so current forward-from-backward results can be resumed without reusing a previous forward branch. Older simple compatible records remain readable; ambiguous or unverified historical state requires a fresh search, rather than a fabricated assignment. Feature state is restored from validated steps for every declared direction. A real stopped/resumed native search is compared against uninterrupted execution, including the earlier backward direction's remaining features. Resume and admission implementation files are included in the search-basis fingerprint; changing that implementation blocks silent reuse of an older basis.

SFS and tuning starts reuse the existing canonical positive-file-ID parser, making accepted numeric strings and integer status/stop requests address the same progress entry. A short process-local lock serializes registration after request validation, and both starts refuse a currently running owner. Validation, fitting, publication and callbacks remain outside the registration lock. This guards one process; it does not qualify distributed leases, operation journals, crash-safe start/ownership, cross-store transactions or full lifecycle recovery.

Thirty-six new regressions cover invalid/terminal/foreign/contradictory resume evidence, valid stopped/interrupted checkpoints, active merged directions, native later-direction stop/replay parity, canonical IDs, duplicate starts and simultaneous registration. These shape and consistency checks do not authenticate externally edited metadata or replace independent scientific review. Existing reference metrics, data, folds, thresholds, skip/coverage and time/retry budgets remain unchanged. Source qualification: [P59 receipt](evidence/p59-qualification-2026-10-14.json). Exact-head six-check/private Linux and separate parent/main qualification remain required; D07 and release/customer gates remain open.
