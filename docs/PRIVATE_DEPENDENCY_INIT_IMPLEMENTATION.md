# Fresh dependency filesystem preparation — P40

After the saved v2 plan and [P36 filesystem initialization](PRIVATE_INSTALLATION_INIT_IMPLEMENTATION.md), prepare a new dependency root:

```sh
sudo python scripts/private_dependency_init.py /approved/plan \
  --expected-plan-sha256 TRUSTED_PLAN_MANIFEST_DIGEST \
  --delivery /approved/dependency-delivery
```

The delivery has exactly `postgres/server.crt`, `postgres/server.key`, `postgres/owner-password`, `job-broker/server.crt` and `job-broker/server.key`. Its two group directories and root are UID/GID 10001 with mode 0700; each bounded, single-link regular file is UID/GID 10001 with mode 0400. Safe absolute ancestors, no links and no ACLs are required. Credentials come from the approved delivery; none are generated. Existing app credentials and selected PostgreSQL/broker CAs are captured from the initialized app root without changing them. PostgreSQL owner/app and decoded broker passwords require at least 32 characters and five distinct characters, with no embedded controls. Broker URLs retain the existing endpoint/TLS contract and must select one of this profile's 16 databases; unsupported values block without rewriting.

The initializer verifies the saved plan, exact initialization binding and P35 path metadata. An existing `dependencies` destination stops before secret reads. It verifies each server certificate against only its captured app CA, current validity, server purpose and exact `postgres`/`job-broker` hostname, and verifies the unencrypted private-key pairing using bounded, noninteractive OpenSSL 3 commands with a fixed environment. It excludes general host trust paths/stores. CRL/OCSP, future certificate lifetime, customer trust-policy approval and secret rotation remain separate qualifications.

A private stage creates `root/dependencies`, a nonsecret fixed profile and receipt, role configuration directories and empty persistent PostgreSQL/broker data directories. Configuration directories/files are root-owned with role-group read access; service users cannot rewrite them. PostgreSQL's fixed native identity is 70:70, Redis is 999:1000. Native image-account verification is required before future startup; preparation does not attest an account it has not run. Data directories are owned by the corresponding service, mode 0700. The dependency root is root-only 0700; profile/receipt are root-only 0600. Configurations, including keys and credentials, are mode 0440 and are intended for read-only container mounts. PostgreSQL supports root-owned keys readable by its service group; see [PostgreSQL TLS](https://www.postgresql.org/docs/17/ssl-tcp.html).

The fixed profile binds exact image IDs, installation/plan/initialization, non-root identities, entrypoints/commands, private-only networking, no published ports, read-only roots, no capabilities, resource limits, bounded tmpfs, mount paths and restart policy. PostgreSQL allows local owner peer access and only the declared application database/role through TLS/SCRAM over IPv4; other local/remote access is rejected. Names are quoted so HBA keywords remain literal, as described in [PostgreSQL HBA rules](https://www.postgresql.org/docs/17/auth-pg-hba-conf.html). The job broker has TLS-only transport, authentication, AOF/every-second fsync and a no-eviction memory policy. Cache stays reconstructible, bounded and without persistence on the internal application bridge; cache authentication/TLS and comprehensive egress policy are not qualified here. Runtime CONFIG/DEBUG/MODULE changes are disabled in both Redis recipes. AOF durability is separate from coordinated restore and does not guarantee zero loss; see [Redis persistence](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/).

Only fully validated bytes are staged, fsynced and atomically published with Linux no-replace semantics. Pre-publication failures remove only this invocation's stage. A competing destination wins without replacement. An interrupted post-publication directory may remain and must be inspected; this command never resumes or overwrites it. Existing PostgreSQL/broker data, application artifacts, credentials and recorded history are preserved. Secret values or their hashes are never emitted in evidence; the profile digest covers only nonsecret specifications.

This step contacts no Docker daemon, starts no service and applies no migrations. The next D07 slice must verify these paths/configurations and native accounts, initialize a fresh database with a non-superuser app role, start the exact profiles and qualify actual TLS/authentication and restart behavior. Storage encryption/capacity/retention, complete dependency hardening, migrations, upgrades/rollback, production recovery and release/value/customer gates remain open.

[P40 source qualification](evidence/p40-qualification-2026-10-12.json) records focused checks and actual owned Linux/OpenSSL fixtures on native images. Existing CI adds these cases on AMD64 and retains all prior application adoption, native jobs, private TLS, full metadata, recovery and browser checks without changing their budgets. Final exact-head CI/merge and separate main receipts are bound on the PR.
