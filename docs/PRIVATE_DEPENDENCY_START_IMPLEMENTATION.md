# Private dependency startup and application DB initialization — P41

Start only the [P40 prepared dependency root](PRIVATE_DEPENDENCY_INIT_IMPLEMENTATION.md):

```sh
sudo python scripts/private_dependency_start.py /approved/plan \
  --expected-plan-sha256 TRUSTED_PLAN_MANIFEST_DIGEST
```

This Linux-root controller rechecks the saved v2 plan, initialization binding and app path metadata. It pins the root-owned dependency tree, requires exact profile/receipt/configuration members, ownership/modes, regular single-link bounded files and no ACLs, and compares the fixed configuration recipes with current app inputs. It rechecks current selected-CA/hostname/key validity rather than trusting the preparation-time certificate result. A root-owned nonblocking installation lock serializes startup attempts. The supported default local/native Docker daemon must use runc; exact Linux image IDs/architecture, fixed dependency entrypoints and native postgres 70:70/redis 999:1000 accounts are verified before creation.

Only PostgreSQL, dedicated TLS job broker and reconstructible cache may start. Exact named containers bind installation, plan, app initialization, dependency initialization and profile digest. Trusted image labels are included exactly alongside those bindings. User/entrypoint/command, complete environment, health-check definition, limits, swap bound, restart, namespaces, read-only root, no capabilities/no-new-privileges, devices/groups/DNS/host mappings, private-only networking, unpublished ports and exact read/write bind paths must match. No missing host bind is auto-created. Foreign/changed containers are neither repaired nor removed. Unknown private-network members block, while exact bound application profiles may remain present.

New PostgreSQL/broker containers require empty prepared storage. Matching interrupted containers can resume against their own bound storage. A recorded successful container that is missing/replaced cannot be silently recreated; it needs a reviewed recovery workflow. Existing paused/dead or changed services are rejected. Partial startup can leave its own bound services/data for inspection; there is no automatic rollback or cleanup of operational resources.

PostgreSQL first initialization uses the delivered owner password and a local peer-authenticated owner. The controller sends credential-bearing SQL only on stdin, with quoted identifiers/literals and no secret-bearing argv/environment/output. It rejects unknown non-system roles/databases and creates only an absent declared application role/database. The application role has login with no superuser, database/role creation, replication, RLS bypass or memberships; ownership/UTF8 are checked. Existing credentials, roles, grants and data are never reset to make a check pass. PostgreSQL error-statement logging is disabled in the fixed recipe so rejected credential-bearing DDL is not logged. The configured HBA rejects remote owner and non-TLS connections; only the literal declared app database/user may use remote TLS/SCRAM.

A bounded disposable helper uses the exact sealed API image, Python isolated mode, UID/GID 10001, private networking and only four read-only app-credential/CA file binds. It has no owner credential, model data, host service/device or Docker socket access. Image/code/environment/resource/isolation/mount identity is inspected before execution. It checks actual authenticated PostgreSQL TLS and current app-role flags/membership, authenticated hostname-verified broker TLS, enabled AOF plus a unique expiring write/read/delete probe, and reconstructible-cache connectivity/AOF disabled. Runtime brokers/caches retain the P40 memory/persistence/control-command recipes; cache authentication/TLS, comprehensive egress policy and dependency capacity remain separate qualification.

After readiness, all three exact active container IDs/profiles and network membership are sampled again. A successful nonsecret receipt is published once as root-only `dependencies/started.json`; retries verify its exact IDs/images/typed claims without overwriting it. Publication is idempotent, and a failed or interrupted attempt cannot grant model-use/installation/release approval. These are sampled technical startup checks, not an atomic future-health guarantee or production disaster-recovery evidence. Bound managed dependencies are also rechecked during P38/P39 application adoption; a prepared managed root or managed labels cannot silently use historical weaker checks. Historical operator-managed installations remain explicitly scoped to their earlier protocol.

This step creates the application database/role but does not run Django migrations or enroll accounts. Current approved schema migration remains an explicit step before application preflight/adoption. Storage encryption/capacity/retention, complete policy hardening, supply authenticity, upgrades/rollback, production recovery, expert isolation and release/value/customer gates stay open.

[P41 source qualification](evidence/p41-qualification-2026-10-12.json) retains the native image-label development rejection and correction, focused cases and real native profiles. The existing AMD64 CI adds a fresh owned Linux-root workflow: prepare/start, repeat without recreation/republication, graceful restart retaining an app-database fixture row, changed-profile rejection without repair, elevated-role rejection without repair, foreign catalog preservation and managed-adoption enforcement. It removes only its own exactly bound containers/networks/socket and exclusive fixture root. All earlier native/private/full metadata/restore/browser gates and their budgets remain. Final exact-head qualification/merge and separate main results are recorded on the PR.
