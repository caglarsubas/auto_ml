# P14 — Exact assistant action approvals and dispatch receipts

Updated 9 October 2026. This packet follows merged [PR #103](https://github.com/caglarsubas/auto_ml/pull/103), whose merge-main CI passed all five jobs. It partially advances D04, D06, D08 and D12 in the [canonical ledger](product-roadmap.json). Complete outcomes and release/customer gates remain open.

Previously, a signed-in client could submit an arbitrary typed action directly to `/execute-action/`. The chat panel also attempted automatic code repair and execution after failures. The panel now separates **Review action**, **Approve this action** and **Cancel review**. Edits, dataset changes, altered approvals and expired or changed recorded inputs require fresh preparation. Late preparation/approval responses cannot dispatch into a different selected dataset or clear a newer review. Unconfirmed cancellation is shown explicitly. Automatic code repair and execution have been removed.

## Authority and receipt scope

An approval authorizes one existing native typed dispatch. Dictionary descriptions can be persisted by that dispatch; most other handlers return settings/events for the frontend pipeline. A completed dispatch receipt does **not** establish that a downstream job started, finished, used immutable inputs, or passed independent review. Job-action messages now say the request was sent to the pipeline. Downstream jobs, human organizational approval, independent review and expert execution require separate authority and evidence.

Preparation records the active Django actor, canonical dataset ID, exact action and JSON payload, normalized optional chat linkage/source, dispatcher environment, input context, a five-minute expiry and a bounded payload budget. Payloads must be finite JSON objects, at most 32 KiB, with at most 100 members per collection and ten nesting levels. The recorded budget allows one typed dispatch and explicitly grants no expert-code or downstream-job authority. Failed or completed approvals are consumed; identical HTTP retries return the retained result and a replay flag rather than redispatching.

The context hashes managed dataset bytes and declaration identity, saved dictionary descriptions, recorded pipeline states and these available native pointers: modeling status, evaluation, split, preprocessing configuration, SFS results, tuning results and current deployment bundle. For ordinal rankings it additionally hashes the live Redis encoding-plan/dictionary inputs; unavailable Redis blocks preparation/dispatch. It never loads a fitted Python object or parses final holdout outcomes. Hashing a file is not permission to inspect its outcomes. The environment pins Python and installed Django/DRF/pandas/numpy versions plus dispatcher and approval-controller source hashes. It describes the typed dispatcher, not every model/job dependency.

Both approval and dispatch compare the current recorded context/environment and expiry. Actor activity is checked server-side, and approval records belong to their actor. Missing, foreign, altered, cancelled, expired and stale confirmations fail with actionable errors. A changed prepared envelope fails its SHA-256 check. These hashes detect changes inside the trusted controller/database boundary; they are not independently signed attestations or defenses against a privileged database administrator.

## Interfaces and failure handling

All browser endpoints use real server sessions and CSRF. Clients first POST the native action to `/api/ai-assistant/prepare-action/`, then submit its `approval_id` and `proposal_sha256` to `/approve-action/`. `/execute-action/` requires that selector plus the exact prepared file/action/payload/source/linkage. `/cancel-action/` closes a pending review. GET `/action-approval/<uuid>/?proposal_sha256=<digest>` returns the actor's retained receipt/result without re-executing it. Expert Python is rejected even with a fabricated approval; inline code and MCP direct execution retain their separate blocked boundaries.

A dataset file lock serializes approval/dispatch operations on the supported local filesystem. The database reservation commits before the native handler runs. Reservation failure prevents dispatch. Completion-write failure leaves an unresolved `dispatching` receipt and returns an error; execution is never silently repeated. A retained in-flight attempt also blocks fresh preparation for that dataset, including by another installation user. The operator must inspect the read-only admin audit and reconcile the outcome; this packet provides no automatic recovery or authority to reset/replay uncertain actions. Actor snapshots survive account deletion.

A failed handler may have partially changed state. Its failure receipt is consumed and repeat requests return that failure. A new proposal still needs explicit review of current recorded state. Publication/adoption of downstream frontend events is outside this idempotence guarantee, including after a lost HTTP response or browser restart.

The additive migration creates approval records and does not alter legacy files/history. Historical action cards require fresh review; historical approvals are never invented. Existing scientific pipelines and supported native handler semantics are retained.
