# Controlled private application adoption — P38

After [fresh filesystem initialization](PRIVATE_INSTALLATION_INIT_IMPLEMENTATION.md) and [network/socket preparation](PRIVATE_INSTALLATION_RESOURCES_IMPLEMENTATION.md), this Linux root controller starts the four application roles from one exact saved plan. It is partial D07: the operator must already have prepared the database, cache and TLS broker and applied current migrations. It does not provision these dependencies, generate credentials, enroll users or authorize model use.

```sh
sudo python scripts/private_installation_adopt.py /approved/plan \
  --expected-plan-sha256 TRUSTED_PLAN_MANIFEST_DIGEST \
  --client-ca /approved/ingress-client-ca.pem
```

Use the host default Docker context at `unix:///var/run/docker.sock`, with a Linux daemon matching the plan's native architecture and all four exact images already loaded. Docker endpoint/context/TLS environment overrides fail. The controller verifies the saved plan and initialization receipt and repeats filesystem checks before Docker operations. Archive verification, authenticated supply and encrypted storage qualification remain separate prerequisites.

The independently selected client CA must be an absolute, non-traversing path to a bounded, single-link root-owned regular PEM file. Ancestors are pinned, root-owned, non-writable by group/others and ACL-free; the file has the same write/ACL restrictions. Its captured bytes must remain consistent during reading. Invalid CA input stops before Docker contact. The CA is explicitly loaded, rather than relying on the host's general trust store. The HTTPS check connects to the declared IPv4 bind address, uses the declared DNS name for SNI/certificate validation and sends the exact declared Host authority.

Networks and socket volume must retain their exact installation/plan/initialization binding. The private network must contain exactly one running, pinned-image operator dependency for each alias `postgres`, `cache` and `job-broker`, plus any existing bound application services; dependencies must have no published ports, no privileged mode and no additional networks. The edge network permits only bound application services. The socket must have its bound local-volume profile and no attachments outside the application project, including stopped containers. These checks establish connection/resource prerequisites, not a complete dependency hardening or persistence profile.

Existing project containers are accepted only when their image, role/binding/profile labels, fixed entrypoint/command, complete environment, UID/GID, working directory, stop timeout, read-only root, capabilities, security options, namespaces, device access, CPU/memory/PID limits, tmpfs, restart policy, networks, mounts and published ports match the exact rederived application profile. Unexpected roles, duplicate roles or altered profiles stop before application startup. No foreign or changed container is repaired or removed.

Before application startup, a bounded, disposable preflight uses the sealed API image's new `preflight` role. It has no published port, no capabilities, a read-only root, private-network access and exactly two read-only binds: app secrets and artifacts. Image, labels, environment, mounts and execution limits are inspected before start. It verifies authenticated PostgreSQL TLS, current migrations and authenticated TLS broker connectivity, and rejects elevated application-role flags, sensitive predefined memberships or membership in elevated roles. It returns without starting an API, worker or dispatcher. Its exact owned container ID is removed on completion or failure. Ordinary existing service entrypoints retain their behavior.

The controller writes the captured Compose profile to a private temporary directory and runs only the four fixed roles with no build, no pull and `--no-recreate`; caller `.env` files are excluded. It inspects all resulting services and checks a CA/hostname-verified anonymous `/api/auth/session/` response. Repeating a successful adoption keeps the same containers. A stopped matching container may be started again; an incompatible version requires a separately reviewed upgrade workflow.

There is no transactional Docker startup or automatic rollback. A startup, subsequent profile or HTTPS failure may leave newly created or already running bound services for inspection. The controller never stops an existing service to undo a failed adoption. Retry only after reviewing the error and current bound state. A timeout is not proof that no service was created. No adoption receipt is emitted until all required checks pass.

The nonsecret receipt records exact service IDs/images, reuse, profile digest, initialization and plan binding, sealed preflight and HTTPS results. `services_adopted` describes technical startup; model-use approval, complete installation/release/expert qualification and production recovery remain false. It does not prove application capacity, durable dependency configuration, future health, user enrollment, firewall/egress policy or customer acceptance.

Qualification uses exclusively owned UUID fixtures. Local ARM64 checks real Compose-created profiles without starting them, plus fail-closed unit/regression cases and the full SQLite matrix. Hosted AMD64 CI adds an actual fresh Linux root: P36 initialization, P37 preparation, synthetic operator dependencies and current migrations, four-role adoption, malformed-CA rejection before startup, repeated adoption without recreation, altered-profile rejection without repair, and elevated-grant rejection preserving existing services. The fixture's temporary admin bootstrap, certificate and data storage are test preparation, not a supported production dependency initializer. It removes only its own bound containers, networks, volume and host root. The existing six CI jobs, full PostgreSQL/private TLS/browser/worker/recovery scenarios and all scientific, timeout, skip, retry and coverage budgets remain.

[P38 source evidence](evidence/p38-qualification-2026-10-11.json) distinguishes observed local checks from the additional hosted acceptance gate; the final exact-head CI/merge receipt is recorded on the PR. Dependency provisioning/hardening, encrypted storage and capacity, authenticated supply, upgrades/rollback, production recovery, expert isolation, clean reproduction, comprehensive accessibility and release/value/customer gates remain open.
